# Event-driven orchestrator channel redesign

Status: implemented and accepted on this Linux workstation. Acceptance cases
1–8 pass with a real Codex child and a real Claude child. They have source regressions, disposable installed-user evidence, and an active
Claude parent/child recheck in the [consumer evidence](isolated-consumer-acceptance-evidence.md)
and [Claude host evidence](claude-host-acceptance-evidence.md). The active
installation uses a staged release candidate of this component.
The existing `inbox`/`answer_ask` tools remain available for recovery. The
managed process path also passed the complete component suite on a real
GitHub `macos-latest` runner at commit `4b3ec17`: 768 tests passed, including
the event-channel subprocess journeys, `ps` identity fallback, orphan
detection, and POSIX process-group launch coverage. See the
[consumer evidence](isolated-consumer-acceptance-evidence.md) for the run ID.
This is channel acceptance, not a claim that every Pitwall release journey is
ready for public release.

## Defect and missed acceptance criterion

The current child-side `ask_orchestrator` writes an ask and blocks. The parent-side `inbox` only returns asks when the parent chooses to call it. When Claude launches a shim through a synchronous tool call, Claude is waiting for that call to finish and cannot reliably call `inbox`; the child is waiting for Claude. A deadline/default or a separate human/auto-answerer can break the stalemate, but neither provides the promised parent-child conversation. Steering has the same delivery weakness when the child does not call `read_steering`.

Our tests proved the transport in isolation: `test_mcp_subagent_tools` answers from a test thread/operator, `test_mcp_orchestrator_tools` checks inbox and answer calls, and one scripted Claude dispatch used the MCP tools successfully. They did not prove that an ordinary Claude orchestrator receives and answers a child's question *while its own dispatch tool is outstanding*. `mcp_channel_registered` checks a config entry, while `doctor._probe_channel_server` checks the role-specific stdio tool lists; neither checks parent-child event delivery in Claude. Calling this “tier 1” from registration alone overstates what works.

## Existing code to reuse

| Concern | Existing implementation | Consequence for this change |
| --- | --- | --- |
| Child execution | `pitwall.agents.dispatch:dispatch_legacy` owns run creation, routing options, lifecycle, prompt injection, timeout, and final receipt; `pitwall.agents.process:run_process` owns provider process-group supervision. | Launch that CLI dispatch in a separate, supervised process. Do not create a second provider runner or new always-on service. |
| Channel state | `RunStore`, `Mailbox`, `channel.read_channel_inbox`, `channel.answer_ask`, and `channel.send_steer` persist validated asks, answers, steers, and receipts. | Build event waits and answer/steer calls over these records. Preserve their existing exclusive-write and default semantics. |
| MCP | `mcp_server.ChannelServer` serves role-specific stdio tools; `mcp_tools.build_server` registers the two current parent tools and three child tools. | Add parent tools in this registration path; preserve child/parent role separation. Server request cancellation must end only the wait, not silently kill a managed dispatch. |
| Claude guard | The plugin has a `PreToolUse` steering gate, but its DAG and ledger tripwires run at `Stop`. Shim agent descriptions are inconsistent about background `Agent` calls. | Add a separate, pre-execution launch guard and reconcile the agent descriptions. The Stop hooks cannot prevent an orphan launch. |
| Capability status | `mcp_registration.render_entry` configures the harness; `capability_inventory.mcp_channel_registered` checks registration; `doctor._probe_channel_server` handshakes with the MCP server. | Report registration, protocol health, host-event support, and proven interactive delivery as distinct states. A default doctor must remain local/read-only and must not spend provider quota. |

## Required user journey

1. Claude starts an external-model dispatch through one Pitwall MCP tool, `dispatch_and_wait`, with structured route, prompt, workspace, timeout, and ask settings. The tool resolves the route through the existing route layer, assigns a full UUID, and launches the existing CLI dispatcher with an argv list, never a shell string. Managed interactive dispatches enable `--routing-ask-support`; they fail preflight if the selected child harness cannot expose the child-side channel. The tool receives a dispatch ID and returns when the child asks, completes, fails, or reaches the tool's bounded wait deadline. Claude does not run a separate `inbox` loop.
2. If the child asks, `dispatch_and_wait` returns an `ask` event with the exact options, default, deadline, and dispatch ID. The child remains blocked in `ask_orchestrator`. Claude can inspect context, ask the user when necessary, then call `answer_and_wait` with the full dispatch ID, ask ID, and chosen option. The existing exclusive answer write records the choice before waiting for another event. A duplicate answer reports the recorded choice without changing it; a conflicting choice is an error. The event must carry the existing `blocked_on` and severity so destructive, spending, schema, and blocking asks still escalate to the operator.
3. A terminal event returns the normal dispatch receipt, outcome, and artifact references. An event-wait timeout returns a `still_running` receipt and a reattach handle; it never guesses an answer or labels the task complete. Claude can call `wait_dispatch` with that handle. The answer deadline is independent of the MCP wait deadline.
4. `steer_and_wait` records a directive and returns either its acknowledgement, the next ask/terminal event, or a bounded `still_running` receipt. It must report an unacknowledged directive honestly.
5. If the parent MCP connection dies, run and mailbox state remain durable. A new parent session can reattach by full dispatch ID. An unanswered ask may be returned again after reconnection; delivery is **at least once**, and answer writes are idempotent. No live child may depend on one MCP request or process staying alive. A lost dispatcher process without a terminal receipt must be reported as an orphan/error, not as `still_running` forever.

The primary interface is an event returned from an outstanding MCP tool call, followed by an explicit answer or steer call. It does not rely on Claude Code reacting to an unsolicited server notification or on a background hook waking an idle model. MCP clients may differ in their support for those behaviors; neither is a release dependency.

## Prevent disconnected launches

During a Pitwall-routed task, Claude must not start an external-model child through a bare `Agent` shim, an arbitrary provider CLI, a direct shim script, a backgrounded Bash call, or a shell-background construct. In particular, `Agent(..., run_in_background: true)` around a shim and `Bash(..., run_in_background: true)` are not acceptable substitutes for the durable dispatcher: both can leave the parent holding only a task ID or partial output instead of an answerable child event. Existing shim agent descriptions already warn against backgrounding, but prompt text is not enforcement.

Add a Claude `PreToolUse` launch guard in the Pitwall plugin for routing-active turns. It inspects the actual `Agent` and shell-tool input *before execution*, including background flags and recognizable shim/provider invocations. It must refuse shim `Agent` types, native agents or `Workflow` scripts that name a shim or provider launch, and `Workflow` scripts it cannot read, while permitting the new managed Pitwall dispatch tool after its capability check succeeds. Native research `Agent` launches are allowed because the host runs `PreToolUse` on their own tool calls under the parent session ([claude-host-acceptance-evidence.md](claude-host-acceptance-evidence.md#subagent-tool-calls-reach-pretooluse)). It denies recognized external launches through any other path and gives Claude the exact managed tool to use. The existing Stop tripwire only detects some misroutes after a turn; it cannot protect this boundary.

The guard must have a narrow, explicit activation signal tied to a Pitwall routing request or workflow, and must not block unrelated user shell commands or ordinary native Claude tasks. A real Claude Code 2.1.278 probe found a stable `session_id` in `PreToolUse`, but an explicit `/pitwall:dag-routing` invocation supplied no routing attribution to that hook. Claude's documented [`UserPromptExpansion`](https://code.claude.com/docs/en/hooks#userpromptexpansion) event carries `command_name` and `session_id` before a user-typed slash command reaches the model. An installed consumer has now shown that this event activates the packaged `/pitwall:dag-routing` guard before its first Bash action. A model-invoked `Skill` call can be caught separately by `PreToolUse`. Continue testing marker lifetime, failed-preflight cleanup, concurrent calls, and other tool forms before claiming complete prevention.

Do not infer routing state from arbitrary prompt text. Treat unrecognized wrappers and arbitrary provider CLI commands as outside the guaranteed detection set rather than claiming complete shell-command interception. A managed launch must carry a dispatch receipt and verified child channel capability; a process merely named `*-shim` or tagged “Pitwall” does not satisfy the rule. If the guard cannot inspect a tool call or the host lacks `PreToolUse`, capability reporting must say enforcement is unavailable. Do not install a machine-wide ban on all subagents. The routing marker ends with the turn once no managed dispatch it launched is still running, even when the host backgrounded the dispatch call.

## Implementation boundaries

- Keep the existing private mailbox as the source of truth, including ask caps, deadlines, exclusive answer writes, receipts, and cleanup. Do not add a cursor or lease unless a test proves the existing exclusive answer write and at-least-once event delivery insufficient. The `defaulted` event is the one delivery record this rule allowed: `launches/<uuid>/defaults_reported.json` (Task 31 test `test_default_is_reported_once_as_an_event`). The current `inbox` remains a recovery/inspection command, not the standard orchestration path.
- Launch the existing CLI dispatcher as an independent process with redirected stdout/stderr, so an MCP wait cancellation or server restart does not kill it. `dispatch_legacy` and `run_process` remain the supervisor and child-process-group owners. Persist launcher PID/start identity and a receipt; detect dead launchers and missing terminal receipts. The waiter observes mailbox and terminal state in bounded intervals inside the tool implementation; that must not require model-driven inbox polling. Validate Linux and macOS process behavior rather than assuming `setsid()` is portable.
- Keep role separation: `dispatch_legacy` already passes `PITWALL_AGENTS_CHANNEL_DISPATCH_ID` and state root to the child, and `ChannelServer` selects tools from that environment. Parent operations must use an exact full UUID and the server's configured private state root; never trust a caller-supplied path or the existing prefix-matching `find_run` for a managed operation. File mode `0700`/`0600` isolates OS users, but the current local MCP tools do not isolate two sessions of the same user. Add a per-run capability or equivalent session binding if cross-session access is a product requirement; test it instead of treating a UUID as authorization.
- Separate static registration/stdio health from interactive capability. The existing doctor can test the MCP handshake without a model request, but a real installed-host exchange is needed to claim interactive delivery. An opt-in live probe may use a provider; default doctor must not. Unsupported hosts must fail managed interactive preflight or use an explicitly selected pause/resume mode, never silently claim live bidirectional communication.
- Native Claude `Agent`/Workflow children use Claude's native lifecycle, which returns completion but does not currently expose a demonstrated mid-task ask-to-parent path. A Claude `Workflow` whose nodes are shim `Agent` types inherits that gap. The Pitwall channel applies to Pitwall-dispatched external CLI children. In a routing-active session that requires bidirectional communication, the guard must refuse shim `Agent` types, native agents or `Workflow` scripts that name a shim or provider launch, and `Workflow` scripts it cannot read; native research `Agent` launches are allowed because the host runs `PreToolUse` on their own tool calls under the parent session ([claude-host-acceptance-evidence.md](claude-host-acceptance-evidence.md#subagent-tool-calls-reach-pretooluse)); dependency ordering must use managed parent dispatch calls. Documentation and UI must state this boundary plainly. Do not imply that installing the MCP server attaches Pitwall identities to native agents.
- Remove or rewrite the shim agent instructions that advertise `run_in_background: true` as a supported per-dispatch option. Until migration, make the launch guard block that option for routed shim work. Guard and skill guidance must agree.
- Preserve the current prompt/file fallback for older callers during migration. Deprecate instructions that make routine `inbox` polling the normal path only after the event-driven path passes release acceptance.

## Acceptance evidence required before claiming the defect fixed

1. In a fresh, installed Claude Code session, Claude calls `dispatch_and_wait` for a real external-model child. The child raises a blocking ask. The parent receives that ask as the tool result without any `inbox` call, answers it, and receives a terminal result through `answer_and_wait`. Record dispatch ID, tool names, event order, and redacted receipts.
2. Repeat with two concurrent children, out-of-order asks, one steer with an acknowledgement, a defaulted deadline, and a child that never calls `read_steering`. Each outcome must be visible and attributed to the correct run.
3. Kill/restart the parent MCP server while an ask is open; reattach from a new session and answer once. Kill/restart the waiter while a child is running; verify the child and receipt survive.
4. Exercise cancellation, a full mailbox, expired/invalid asks, duplicate/conflicting answers, a parent that never returns, and a launcher that dies without a result. No branch may hang indefinitely, silently lose an ask, or apply anything other than the child's validated, recorded default when its deadline expires.
5. Run fresh foreground and background native Claude `Agent` tasks. Distinguish completion delivery from mid-task question/answer delivery. The guard must refuse shim `Agent` types, native agents or `Workflow` scripts that name a shim or provider launch, and `Workflow` scripts it cannot read; native research agents are allowed because the host runs `PreToolUse` on their own tool calls under the parent session (see [claude-host-acceptance-evidence.md](claude-host-acceptance-evidence.md#subagent-tool-calls-reach-pretooluse)). Verify Pitwall does not advertise a native task as an interactive Pitwall dispatch.
6. Package and install the changed component in an isolated consumer, then run the same journey through the installed entrypoint. Source-tree tests alone are insufficient. Only after this passes should the active workstation installation be updated and rechecked.
7. First capture actual Claude hook payloads for foreground/background `Agent`, Bash, and the managed MCP tool, including session identity and background flags. In an explicitly routing-active Claude session, attempt a native research `Agent`, a backgrounded shim `Agent`, a native `Agent` that attempts a shim launch through its own `Bash` call, a backgrounded shell shim, a foreground direct shim, and a recognizable direct provider launch. Verify `PreToolUse` allows only the native research `Agent` and denies each recognized external launch *before a process starts*, explains the managed route, and leaves no orphan child. Verify a managed dispatch proceeds. Outside that session, verify unrelated shell and native-agent work is unaffected. Report opaque wrapper commands as a detection limit.
8. Disable the guard or use a host without `PreToolUse`; verify capability reporting says launch enforcement is unavailable and no end-to-end communication claim is made. Exercise disguised/unrecognized shell wrappers and report the detection boundary instead of silently counting them as protected. Doctor reports `channel.launch_enforcement` as WARN 'launch enforcement unavailable' when the plugin or its PreToolUse guard is missing, PASS when installed and enabled, and SKIP without a Claude configuration.

## Sequencing

First verify Claude's real hook payload/session marker behavior and MCP tool-return behavior with a bounded installed-host experiment. Then add the parent MCP tools and independent launcher around the existing CLI dispatcher, with fake-provider integration tests for event ordering, timeout, cancellation, reattachment, and orphan detection. Add the launch guard once its activation mechanism is proven. Validate a real Claude-hosted child/parent exchange, blocked disconnected launches, and the restart path. Update the three host skills, shim agent descriptions, channel guide, doctor/capability reporting, and installed-user tests in the same change. Retire polling language only after the installed journey succeeds.
