# MCP 2026-07-28 gap analysis: broker and channel servers

Date: 2026-10-06. Branch inspected: `feat/zcode-harness` at `836c4fba`.

revision, `2026-07-28`, and its documentation. Every finding about Pitwall cites the code
and the command that showed it. Every finding about the protocol cites the page it comes
from. The remediation plan is
[2026-10-06-mcp-alignment-channel-and-run-store.md](../superpowers/plans/2026-10-06-mcp-alignment-channel-and-run-store.md).

## 2. What changed in 2026-07-28

The `2026-07-28` revision is a breaking release. The changes that matter for Pitwall:

1. **Stateless protocol.** The `initialize` / `notifications/initialized` handshake is
   gone. Every request carries `io.modelcontextprotocol/protocolVersion` and
   `io.modelcontextprotocol/clientCapabilities` in `params._meta`, and should carry
   `io.modelcontextprotocol/clientInfo`. A request missing a required field is rejected with
   `-32602`. Servers must not infer anything from earlier requests on the same connection
   ([base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)).
2. **`server/discover` is mandatory.** Servers must implement it. It returns
   `supportedVersions`, `capabilities`, optional `instructions`, `ttlMs`, `cacheScope`, and
   `serverInfo` in `_meta`
   ([discover](https://modelcontextprotocol.io/specification/2026-07-28/server/discover)).
3. **Version negotiation per request.** An unsupported version returns
   `UnsupportedProtocolVersionError` (`-32022`) with `data.supported` and `data.requested`
   ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).
4. **`resultType` on every result.** `"complete"` for ordinary results, `"input_required"`
   for multi round-trip interim results.
5. **Caching hints are required.** Results of `server/discover`, `tools/list`,
   `prompts/list`, `resources/list`, `resources/templates/list`, and `resources/read` must
   carry `ttlMs` (an integer of at least 0) and `cacheScope` (`"public"` or `"private"`)
   ([caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)).
6. **Servers never send requests.** Elicitation, sampling, and roots travel inside an
   `InputRequiredResult` and come back on a retry
   ([multi round-trip requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)).
7. **`subscriptions/listen` replaces `resources/subscribe` and the HTTP GET stream.**
   Supporting the message patterns, subscribe-and-notify included, is mandatory for every
   implementation
   ([subscriptions](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions)).
8. **`ping`, `logging/setLevel`, and `notifications/roots/list_changed` are removed.** The
   log level is set per request.
9. **Error codes are partitioned.** `-32000` to `-32019` is legacy: new implementations
   should not use it, and `-32002` keeps its old meaning, "resource not found". `-32020` to
   `-32099` is reserved for the specification: `-32020` HeaderMismatch, `-32021`
   MissingRequiredClientCapability, `-32022` UnsupportedProtocolVersion. Codes for purposes
   the specification does not define should be allocated outside `-32768`…`-32000`.
10. **Roots, Sampling, Logging, Dynamic Client Registration, and HTTP+SSE are
    deprecated.** The earliest removal is the first revision on or after 2027-07-28
    ([deprecated registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)).
11. **Tasks moved to an official extension**, `io.modelcontextprotocol/tasks`.
12. **Tool schemas may use any JSON Schema 2020-12 keyword.** `structuredContent` may be
    any JSON value, and tools should be returned in a fixed order.

The specification defines three eras. **Modern** means per-request metadata (2026-07-28).
**Legacy** means the `initialize` handshake (2025-11-25 and earlier). **Dual-era** means
both. A dual-era server serves a request statelessly when it carries modern `_meta`, and
serves an `initialize` with legacy semantics. In the specification's compatibility table,
"Modern client, Legacy server" is the one combination that **fails**.

The Python SDK documentation now says "You must use the Python MCP SDK 2.0.0 or higher"
(build-server and build-client guides) and uses `from mcp.server import MCPServer`.

### F01. Broker serves the legacy era only; the SDK pin blocks 2026-07-28 (High)

**Specification.** Servers MUST implement `server/discover`. Every request carries version
and capabilities in `_meta`, and an unsupported version returns `-32022`. Every result
carries `resultType`. Cacheable results carry `ttlMs` and `cacheScope`. Results should
carry `io.modelcontextprotocol/serverInfo` in `_meta`. Supporting the message patterns,
`subscriptions/listen` included, is mandatory.

**Pitwall.**
- **The pin.** `pyproject.toml:31` pins `"mcp>=1.28.1,<2"` (present since
  `d1ad383e Initial public release`). The installed SDK is 1.28.1, whose
  `mcp/types.py:27` sets `LATEST_PROTOCOL_VERSION = "2025-11-25"` and whose
  `shared/version.py:3` supports `2024-11-05` through `2025-11-25`. A search of the
  installed SDK for `server/discover` or `2026-07-28` finds 0 files.
- **The current SDK.** PyPI's latest is `mcp` 2.3.0, which depends on `mcp-types==2.3.0`.
  Its `mcp_types/version.py` lists `HANDSHAKE_PROTOCOL_VERSIONS` (2024-11-05 through
  2025-11-25) and `MODERN_PROTOCOL_VERSIONS = ("2026-07-28",)`. Its runner
  (`mcp/server/runner.py`) serves both eras: an `initialize` negotiates a handshake version,
  and a request carrying modern `_meta` is served statelessly. Its lowlevel server
  registers `server/discover` (`mcp/server/lowlevel/server.py:460`), fills cache hints from
  `cache_hints=` (`mcp/server/caching.py`), and serves `subscriptions/listen` through
  `ListenHandler`.
- **Breaking changes in SDK 2.** `mcp.server.fastmcp` is removed: importing it raises
  `ModuleNotFoundError` pointing at `mcp.server.mcpserver.MCPServer`. `McpError(ErrorData)`
  becomes `MCPError(code, message, data)` in `mcp/shared/exceptions.py`. Result models use
  snake_case fields (`structured_content`, `is_error`) with camelCase aliases.

**Impact.** Clients that support both eras probe `server/discover`, get an error, fall back
to `initialize`, and work. Clients that only speak 2026-07-28 cannot use the broker. The
upgrade touches 29 files that import the SDK (`src/pitwall/mcp/__init__.py`,
`registry.py`, `safe_boundary.py`, `error_adapter.py`, `tools/onboarding.py`,
`tools/provider_operations.py`, `tools/routing.py`, `tools/release_acceptance/inventory.py`,
and 21 test files).

### F02. Channel serves the legacy era only (High)

**Specification:** as F01.

**Pitwall.**
- `src/pitwall/agents/mcp_server.py:22` declares
  `SUPPORTED_PROTOCOL_VERSIONS = ("2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05")`.
- `ChannelServer._dispatch` handles `initialize`, `ping`, `tools/list`, `tools/call`, and
  `notifications/cancelled`. Every other method gets `-32601`.

Live probe ([A.3](#a3-channel-stdio-probe)):

```text
initialize (protocolVersion 2026-07-28) -> result.protocolVersion "2025-11-25"
server/discover                         -> error -32601 "method not found: server/discover"
```

No result carries `resultType`, `tools/list` has no `ttlMs` or `cacheScope`, and nothing
reads `params._meta` except `progressToken` in `_start_call`.

**Impact.** As F01, for every harness the channel is registered with:

| Harness | Registration file |
|---|---|
| Claude Code | `claude mcp add-json` |
| Codex | `config.toml` |
| Copilot CLI | `mcp-config.json` |
| OpenCode | `opencode.json` |
| Kimi | `mcp.json` |
| Cline | `cline_mcp_settings.json` |
| Qwen Code | `settings.json` |
| ZCode | `config.json` (`mcp.servers`) |

These are written by `mcp_registration.render_entry` for every harness in
`capability_inventory.CHANNEL_HARNESSES`. The merged plan adds Grok, Antigravity, Muse, Hermes, and
goose, so the impact grows to thirteen harnesses. Once a harness adopts a client that
only speaks 2026-07-28, `ask_orchestrator` and the managed dispatch tools stop working,
and only the file-based fallback (pause and exit 75) remains.

### F03. Broker returns an unknown tool as a tool result, not `-32602` (Medium)

**Specification.**
- [Tools, error handling](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling):
  "Protocol Errors … Unknown tool … are returned as standard JSON-RPC errors" with code
  `-32602`.
- The schema's `InvalidParamsError` lists "Tools: Unknown tool name or invalid tool
  arguments".

**Pitwall.** Calling `no_such_tool` through the broker's `tools/call` handler
([A.2](#a2-broker-error-probe)) returns:

```json
{"content":[{"type":"text","text":"{\"error\": \"tool_execution_failed\"}"}],
 "structuredContent":{"error":"tool_execution_failed"},"isError":true}
```

FastMCP raises `ToolError("Unknown tool")`, and `safe_boundary._stable_error_payload` turns
it into the generic code. SDK 2 behaves the same way: `ToolManager.call_tool` raises
`ToolError(f"Unknown tool: {name}")`, and `MCPServer._handle_call_tool` returns
`is_error=True`. The fix therefore belongs in Pitwall's boundary, not the SDK. The channel
already answers correctly (`-32602 unknown tool: nope`).

### F04. Channel accepts undeclared arguments (Medium)

**Specification.**
- [Tools, security considerations](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#security-considerations):
  "Servers MUST: Validate all tool inputs".
- The base protocol: "Schemas MUST be valid … implementations MUST validate".

**Pitwall.** Every channel tool advertises `"additionalProperties": False`
(`mcp_tools.py`, for example `INBOX_TOOL`), but `ChannelServer._start_call` passes the
argument dict straight to the handler. Live probe: `tools/call inbox {"bogus": 1}` returned
`isError: false` with the inbox payload. The broker enforces the same rule correctly
(`safe_boundary.install_safe_call_boundary` rejects undeclared keys with
`invalid_tool_arguments`).

### F05. No tool annotations on any tool (Medium)

**Specification.**
- [Tool data type](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool)
  and schema `ToolAnnotations`: `readOnlyHint` (default false), `destructiveHint` (default
  **true**), `idempotentHint` (default false), and `openWorldHint` (default **true**).
- Clients use these hints, together with "prompt for user confirmation on sensitive
  operations", to decide when a human must approve a call.

**Pitwall.** The broker probe ([A.1](#a1-broker-tool-list-probe)) reports
`with annotations: 0` of 81. The channel's nine tool dictionaries have no `annotations`
key. Because the defaults are "destructive" and "open world", a conforming host treats
read-only tools such as `pitwall_budget_status` exactly like
`pitwall_runpod_delete_volume`. Hosts that prompt on destructive tools prompt on all 81;
hosts that don't prompt get no signal at all. Paid or irreversible tools affected:

| Group | Tools |
|---|---|
| RunPod pods | `pitwall_runpod_terminate_pod`, `pitwall_runpod_action_pod` |
| RunPod deletes | `pitwall_runpod_delete_endpoint`, `pitwall_runpod_delete_template`, `pitwall_runpod_delete_volume`, `pitwall_runpod_delete_registry_auth` |
| Registry auth | `pitwall_runpod_replace_registry_auth` |
| Volume files | `pitwall_volume_delete_object`, `pitwall_volume_upload_object` |
| Budget and spend | `pitwall_budget_set`, `pitwall_serve_model`, `pitwall_lease_pod`, `pitwall_submit_job`, `pitwall_submit_inference` |
| Channel | `dispatch_and_wait` |

### F06. Broker tools have no titles and most parameters are undocumented (Medium)

**Specification.** `Tool.title` is the human-readable display name; display precedence is
`title`, then `annotations.title`, then `name`. The architecture guide lists `title`
alongside `name`, `description`, and `inputSchema`. Parameter `description` fields are the
model's only per-argument guidance.

**Pitwall.**
- `with title: 0` of 81. The channel's tools all have titles.
- `params: 207 with description: 30` ([A.2](#a2-broker-error-probe)). Pydantic-generated
  titles such as `"Capability Class"` are the only text for the other 177. Undocumented
  parameters include `request` on all 21 onboarding and RunPod-resource tools, `intent` on
  three tools where it has three different meanings, `payload`, `confirm_delete`,
  `confirm_overwrite`, and `content_base64`.
- SDK 2's `func_metadata` does not parse docstrings, so descriptions have to be attached
  explicitly.

### F07. Every broker `outputSchema` is the generic `{type: object}` (Medium)

**Specification.**
- [Output schema](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#output-schema):
  "If an output schema is provided: Servers MUST provide structured results that conform."
- [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices)
  use `outputSchema` to generate typed APIs for programmatic tool calling.

**Pitwall.** All 81 tools advertise
`{"additionalProperties": true, "title": "<name>DictOutput", "type": "object"}`. FastMCP
derives it from the `dict[str, Any]` return annotation. It is valid but tells a client
nothing, and hosts that generate types from it get `Record<string, any>`. A schema that
carries no information is worse than none, because clients treat a present schema as a
contract.

### F08. Broker error results give no actionable detail (Medium)

**Specification.** "Tool Execution Errors contain actionable feedback that language models
can use to self-correct and retry with adjusted parameters … Input validation errors"
([tools, error handling](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling)).

**Pitwall.** `pitwall_models_fit` called with `{"model": 5, "bogus": 1}` and with
`{"model": null}` both return only `{"error": "invalid_tool_arguments"}`. The boundary
deliberately reflects nothing from the request (`safe_boundary.py` docstring). The model
cannot tell which argument to fix. Naming the failing parameters, or listing the declared
ones, fixes this without echoing any value: the names come from Pitwall's own schema. SDK 2
already logs exactly that ("Field names only: the rejected values are the caller's data",
`MCPServer._handle_call_tool`). Budget refusals already carry a remedy (`BUDGET_REMEDY`),
which is the pattern to extend.

### F09. No rate limiting of tool calls (Medium)

**Specification.** [Tools, security considerations](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#security-considerations):
"Servers MUST … Rate limit tool invocations".

**Pitwall.** No call-rate control exists in `src/pitwall/mcp/` or in the channel.
`grep -rl 'rate.limit'` over those trees matches only the string `rate_limited` in
`error_codes.py`, which is the RunPod provider's own refusal. The budget gate limits
spend, not call rate. The channel's per-run ask cap limits asks, not calls.

### F10. Broker sends no `instructions`, and its tool list is 104 KB (Low)

**Specification.** `DiscoverResult.instructions` (and the legacy `InitializeResult`) carries
"natural-language guidance for LLMs on how to use this server effectively". The client
best-practices page explains the token cost of large tool catalogues.

**Pitwall.** `mcp.instructions` is `None`. The 81 tool definitions serialize to 103,892
bytes (about 26k tokens). The channel sets `instructions`. The broker's catalogue-first,
preview-then-apply, and idempotency-key conventions exist only in individual tool
descriptions.

### F11. Error class codes use the legacy range, and our documentation misstates them (Low)

**Specification.** In the
[error code policy](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#error-codes),
`-32000` to `-32019` is legacy: new implementations SHOULD NOT use it, and `-32002`
retains the meaning "resource not found". Application codes SHOULD be allocated outside
`-32768`…`-32000`.

**Pitwall.**
- `error_codes.py` assigns:

  | Code | Class |
  |---|---|
  | `-32000` | fallback |
  | `-32001` | authn/z |
  | `-32002` | budget and spend |
  | `-32003` | validation |
  | `-32004` | upstream |
  | `-32005` | conflict |

- **The numbers never reach the wire.** `safe_boundary` returns every exception as an
  `isError` result carrying only a string code. Probe [A.4](#a4-safe-boundary-flattening)
  raised `McpError(code=-32002, data={"error": "budget_exhausted"})` from a tool, and the
  client received `{"error": "budget_exhausted"}` with no number.
- **Our documentation says otherwise.** `docs/sdlc/03-mcp-server.md` §3.4 says "refusal
  surfaces as `-32002`", and its `error_codes` table and §6 say MCP clients receive these
  numbers.
- **The numbers would leak under SDK 2.** `MCPServer.call_tool` documents that an
  `MCPError` raised by a tool is "passed through unchanged". Once the boundary is ported,
  any path that escaped it would put a legacy-range code on the wire.

### F12. Relay emits `-32004` on the wire (Low)

**Pitwall.** `relay.py` sets `ERROR_CODE = -32004`, and `Relay._fail` sends it, with
`data.error` set to `mcp_server_unavailable` or `mcp_server_restarted`, when the child
server is down or restarted. The code is in the legacy range. It was also the draft number
for UnsupportedProtocolVersion before it was renumbered to `-32022`.

### F13. Channel drops a request with a null `id` (Low)

**Specification.** Requests "MUST include a string or integer ID … the ID MUST NOT be
`null`" ([base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)).
A malformed request gets `-32600`.

**Pitwall.** `ChannelServer._dispatch` treats `request_id is None` as a notification and
returns without a response. The probe sent `{"id": null, "method": "ping"}` and got no
reply; the following request, id 6, was answered.

### F14. `pitwall mcp serve broker --json` writes non-MCP bytes to stdout (Low)

**Specification.** "The server MUST NOT write anything to its `stdout` that is not a valid
MCP message" ([stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)).

**Pitwall.**
- `cli/mcp.py:cmd_mcp` calls `out.emit()`, and `Output.emit` (`cli/output.py:129`) writes
  indented JSON to `sys.stdout` before `mcp.run(transport="stdio")`.
- `docs/sdlc/18-cli.md:722` documents this as intentional.
- Registrations launch the server without `--json` (`mcp_install._SERVE_ARGS`), so only
  manual invocations are affected. A client launched that way reads a multi-line JSON
  object as its first protocol line.

### F15. Relay forwards non-JSON child output to the client (Low)

**Pitwall.** `Relay._from_child` writes every child stdout line to the client, including
lines that fail `json.loads` (`message = None` falls through to `self._write(line…)`). A
child that writes stray output (F14, or a dependency calling `print`) corrupts the
client's stream through the relay.

### F16. Channel internal errors echo exception text (Low)

**Specification.** Servers MUST "Sanitize tool outputs". The security best-practices page
advises returning generic messages to clients and keeping detail in local logs.

**Pitwall.** `ChannelServer._start_call` returns `f"internal error: {exc}"` for an
unexpected exception. The broker returns `tool_execution_failed` without any text. The
traceback already goes to stderr (`traceback.print_exc`).

### F17. Broker capabilities advertise prompts and resources that do not exist (Low)

**Specification.** Servers that declare `prompts` or `resources` MUST answer their list
methods. Advertising a feature a server does not offer misleads hosts that build a UI from
`server/discover`.

**Pitwall.** The FastMCP capabilities probe returns
`{'prompts': {'listChanged': False}, 'resources': {'subscribe': False, 'listChanged': False}, 'tools': {'listChanged': False}}`,
but the broker registers no prompts or resources. SDK 2 derives capabilities from which
handlers are registered (`Server.get_capabilities` checks `"prompts/list" in self._request_handlers`),
and `MCPServer.__init__` always registers them.

### F18. The doctor probe only exercises the legacy handshake (Low)

**Pitwall.** `doctor._probe_channel_server` sends `initialize` and `tools/list` and
compares tool names. After F02 is fixed, `channel.mcp_server` would still report PASS for
a channel that fails modern clients. Without a modern probe, doctor cannot see a
regression in the stateless path.

## 4. Areas that already conform

| Area | Rule | Pitwall |
|---|---|---|
| Transport choice | stdio servers SHOULD NOT use the OAuth flow and should take credentials from the environment ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)) | Both servers are stdio only; `__main__.py` and `cli/mcp.py` refuse network transports; credentials come from the environment |
| Credential handling | Pass secrets per server, never by value in config ([local server security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security)) | `mcp_install.FORWARDED_ENV` forwards by reference; channel registrations use `${VAR}` forms |
| Supply chain | Pin artifacts; run isolated | `Dockerfile.mcp` pins the Python base image by digest, runs as UID 10001, removes `pip` |
| Cancellation | stdio clients send `notifications/cancelled`; the server stops work and sends no response | `ChannelServer._dispatch` sets the in-flight event; `ToolCancelled` suppresses the response |
| Progress | `progress` must increase | `_start_call.progress` increments a counter |
| Shutdown | Exit promptly at EOF on stdin | `ChannelServer.serve` returns after the read loop and joins workers for 5 seconds |
| Tool names | 1–128 characters from `[A-Za-z0-9_.-]` | All 81 broker names and 9 channel names match |
| Fixed order | `tools/list` SHOULD be deterministic | `TOOL_REGISTRY` and `_visible()` order is static |
| State handles | Handles opaque, random, bounded; not authentication | Dispatch IDs are UUIDs; `orchestrator-channel.md` says "A dispatch ID is a handle, not a credential" |
| Deprecated features | New implementations SHOULD NOT adopt Roots, Sampling, Logging | Neither server uses them |
| `$ref` handling | No network dereferencing of `$ref` | Schemas use local `$defs` only |

## 5. Adoption opportunities

These are not violations. They become available once F01 and F02 are fixed.

- **O1. The Tasks extension (`io.modelcontextprotocol/tasks`) matches work we built by hand.**
  - Broker: `pitwall_submit_job`, `pitwall_get_job_status`, `pitwall_get_job_result`, and
    `pitwall_cancel_job` follow a submit-and-poll pattern. That corresponds to
    `CreateTaskResult`, `tasks/get`, and `tasks/cancel`.
  - Channel: `dispatch_and_wait`, `wait_dispatch`, and `still_running` reattach to a
    durable handle. The ask and answer exchange is the extension's `input_required` state
    plus `tasks/update`.
  - The extension is opt-in, and the client matrix lists no harness that supports it yet.
- **O2. Resources.** Read-only data the broker serves through tools today (the capability
  catalogue, the gateway catalogue, the audit log, model dossiers) could be resources with
  `ttlMs` and `cacheScope`.
