# serve-model: decisions (interactive walkthrough, 2026-08-27)

Recorded from the operator's answers. These supersede the recommendations in DESIGN-QUESTIONS.md.

| # | Decision | Consequence |
|---|---|---|
| 1 | **Weights: cold download at pod boot in v1**; per-DC network-volume HF cache documented as the operator pattern via existing `network_volume_id`/`data_center_id`; real pre-warm (`hf download` + `hf cache verify`) is a follow-up that replaces the marker script. | Engines download at start; container disk sized from dossier; `HF_HOME`/`LLAMA_CACHE` set to the volume when one is attached. |
| 1b | **HF token: broker-side `PITWALL_HF_TOKEN`**, injected as `HF_TOKEN` into the launch env only for gated repos; never persisted in `provider.config`; redacted from launch payloads, audit rows, dry-run output, logs. | New setting + redaction list in the launch env builder. |
| 2 | **Templates: accept any RunPod pod template id** (official, community, or user) as the launch input; Pitwall supplies `dockerStartCmd`/env/ports at pod create and validates the template is a pod (non-serverless) template. Today's image-keyed generated template remains the fallback when no id is given. Config-hash-keyed generation is documented as future. | `template_id` in serve provider config + CLI `--template-id`; RunPod has no official engine templates (authenticated snapshot in runpod--templates-and-hub.md). |
| 3 | **Engines: vLLM + llama.cpp in v1**; SGLang later. | `engine` becomes a field of the serve contract (start-command shape, readiness path, served-name flag per engine). **Contract addition — flag to the routing side.** |
| 4 | **GPU names: fix now, separate commit.** Canonical tuple → live `gpuTypes.id`; tested alias map for the five drifted names; add the new classes from the live snapshot (`runpod--gputypes-live.json`: RTX 5090, RTX PRO 4000/4500/5000/6000 variants, H100 PCIe, RTX 3090, B300, …). | Own commit on `feat/serve-model` before slice 3. |
| 5 | **Dossiers: PyYAML pinned runtime dependency; dossier YAML front matter is the single source of truth**, read directly at runtime. Dossiers live in `docs/models/`. The hardware×model matrix is a derived YAML view read the same way. | New dep; a `pitwall.models` catalog package with a validated schema. |
| 6 | **TUI: full launch with type-to-confirm** — catalogue → hardware fit (per quant, with cost) → preview → confirmation modal → launch. | First write action in the console; `serve.launch` confirmation mapping; tests for every state. |
| 7 | **Readiness: arm the proxy only after `GET /v1/models` lists the served id.** Arming moves out of the lease-readiness hook into `serve_model` after verification. `startup_timeout_s` comes from the dossier's startup estimate (default 1,800 s). | Slice-1 `arm_serve_provider` call site moves; lease-readiness contract note; plan T13 updated before slice 3 runs. |
| 8 | **Scope: model × quant × hardware selection is a first-class feature.** No limit on GPU count; every (model, variant/quant) row in the matrix is selectable; for a chosen model the tool shows each quant's hardware options with cost; per-row confidence is informational. Non-chat models stay listed with `fits_openai_proxy: false`. | The matrix is a product surface (CLI `models`/`fit` commands, TUI fit screen, MCP tool), not a v1 gate. |
